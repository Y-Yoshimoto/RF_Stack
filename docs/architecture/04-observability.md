# 04. システム監視の観点

> ステータス: ドラフト v0.5
>
> **現フェーズでは実装しない。** 設計・実装時に「後から監視できる形になっているか」を確認するための観点を定める。
> 01 の CP ダッシュボード（テナントの利用状況 = 事業の指標）と、本書の監視（システムの健全性 = 運用の指標）は目的が異なるため分けて考える。

---

## 1. 方針

- **テナントを意識した監視**: マルチテナント SaaS では「全体は正常だが特定テナントだけ遅い・失敗している」が起こる。指標とログはテナント単位で絞り込めるようにする
- **シグナルの 3 本柱**: ログ（[03](03-conventions.md) 6 章）、メトリクス、トレース。いずれも `request_id` / `trace_id` で相互に辿れるようにする
- **アプリは出すだけ**: 収集・保管・可視化・通知は外部の基盤（例: ログ収集 → 可視化ツール）が担う。アプリは標準出力と公開エンドポイントで情報を出す
- **監視のための設計を今やっておく**: 構造化ログ・利用記録・ヘルスチェック・テナントコンテキストの伝搬は今のフェーズで実装し、監視基盤だけを後から足せるようにする

---

## 2. ヘルスチェック

| エンドポイント | 用途 | 確認内容 |
| --- | --- | --- |
| `/api/v1/public/health/live` | プロセスの生存（再起動判定） | プロセスが応答するか。依存先は見ない |
| `/api/v1/public/health/ready` | トラフィックを受けられるか | CP DB・AP DB・Redis への接続、Keycloak の到達性（タイムアウト短め） |

- ready の失敗理由はログに出し、レスポンスには依存先の名前と可否だけを返す（接続文字列等は返さない）

---

## 3. メトリクス

### 3.1 リクエスト（RED）

| 指標 | 単位 | 内訳 |
| --- | --- | --- |
| リクエスト数 | 件/秒 | `plane`, `route`, `method`, `status` |
| エラー率 | % | 同上（5xx と 4xx を分ける） |
| 処理時間 | ms（p50 / p95 / p99） | 同上 |

- `tenant_id` を時系列の内訳に入れると系列数が爆発するため、**メトリクスには入れない**。テナント別の分析はログ（利用記録）で行う。上位テナントだけを別系列にする等は監視基盤の導入時に決める

### 3.2 リソース（USE）

| 対象 | 観点 |
| --- | --- |
| API サーバー | CPU、メモリ、ワーカー数、イベントループの遅延 |
| PostgreSQL | 接続数（ロール別）、コネクションプールの待ち、遅いクエリ、ロック待ち、DB サイズ（DB 別） |
| Redis | メモリ、セッション数、退避（eviction） |
| Keycloak | 応答時間、レルム数、ログイン失敗数 |

### 3.3 マルチテナント固有

| 観点 | 内容 |
| --- | --- |
| ノイジーネイバー | テナント別のリクエスト量・処理時間の偏り（利用記録から集計） |
| テナント分離の異常 | RLS でテナントコンテキスト未設定のまま実行されたクエリ（0 件で返るため気づきにくい）を検知できるよう、`app_runtime` でコンテキスト無しのクエリを WARNING ログに出す |
| 認証の異常 | テナント別のログイン失敗数、許可リスト外のレルムからのトークン |
| ライフサイクル | 払い出しの所要時間・失敗数、`PROVISIONING` / `DEPROVISIONING` の滞留数 |
| 定期ジョブ | ジョブ毎の成否・所要時間・最終成功時刻 |

---

## 4. トレース

- 将来 OpenTelemetry を導入し、ブラウザ → BFF → DB / Keycloak の呼び出しを追えるようにする
- 導入までは `request_id` で代替する。外部呼び出し（Keycloak Admin API 等）のログにも `request_id` を付ける
- トレースの属性に `tenant_id` を付ける（トレースはサンプリングされるため系列数の問題が無い）

---

## 5. アラートの候補

| 種別 | 条件の例 | 重要度 |
| --- | --- | --- |
| 可用性 | ready が連続失敗、5xx 率が閾値超過 | 高 |
| 性能 | 一覧 API の p95 が 500ms 超過（01 の非機能要件） | 中 |
| 払い出し | 払い出し失敗、`PROVISIONING` の滞留 | 高 |
| 定期ジョブ | `metrics_snapshot` / `tenant_purge` が 1 日以上成功していない | 中 |
| セキュリティ | ログイン失敗の急増、CSRF 検証失敗の急増、許可リスト外のトークン | 高 |
| テナント分離 | テナントコンテキスト無しのクエリの発生 | 高 |
| 容量 | DB・Redis のディスク / メモリの逼迫 | 中 |

---

## 6. SLO（たたき台）

| 対象 | SLI | 目標 |
| --- | --- | --- |
| AP API | 5xx 以外の応答の割合 | 99.5%（月間） |
| AP API（一覧） | 500ms 以内の応答の割合 | 95% |
| 払い出し | 30 秒以内に完了した割合 | 95% |

本番の要件が決まった段階で見直す。

## 7. 実装時に確認すること（チェックリスト）

- [ ] ログに `plane` / `tenant_id` / `user_id` / `request_id` が付いているか
- [ ] 秘匿値がログに出ていないか
- [ ] 外部呼び出しにタイムアウトがあり、失敗がログに残るか
- [ ] 定期ジョブの成否が実行履歴に残るか
- [ ] 新しい API の `route` がテンプレート形式でログに出るか
- [ ] ヘルスチェックに新しい依存先を追加したか
