# 05. 決定事項（共通基盤）

> テーマ固有の決定事項は各テーマの仕様書に記載する。
> 決定を覆す場合は、行を消さずに「改訂」として新しい行を追加し、経緯を残す。

## 1. 決定事項

| # | 論点 | 決定内容 | 根拠・参照 |
| --- | --- | --- | --- |
| 1 | テナント識別の URL 方式 | **パス方式** `/{tenant_code}`（接頭辞なし、予約語で CP 等と区別） | 01 §5 |
| 2 | 払い出しの実行方式 | **API 内で同期実行**。見直しは 2 章 #2 | 01 §6.2 |
| 3 | メールアドレスの一意性 | **テナント内で一意**（別テナントの同一アドレスは別ユーザー） | 01 §8 |
| 4 | テナント削除の猶予期間 | **30 日**。期間中はデータを保持するが、復元 API は当面提供しない | 01 §6.3 |
| 5 | アクティブユーザー | 「一定期間内に AP API を利用したユーザー」。本フェーズは**利用記録のログ出力まで** | 01 §6.4、03 §6.3 |
| 6 | テナントの識別子 | 内部 ID は `tenant_id`（UUID）、URL・認証領域名は `tenant_code` | 01 §5.1 |
| 7 | テナント削除のライフサイクル | `PENDING_DELETION` → 30 日後に `DEPROVISIONING` → `DELETED`。テナントコードは再利用しない | 01 §6 |
| 8 | 定期実行 | API サーバーに組み込み、ジョブ本体は分離可能にする | 01 §12.1、02 §5.5 |
| 9 | ユーザーの作成タイミング | 作成時に IdP と AP DB の両方へ事前作成。メールは送らず一時パスワード方式 | 01 §8 |
| 10 | `saas_viewer` ロール | CP の参照専用ロール | 01 §7.5 |
| 11 | フロントと API のオリジン | 同一オリジン（リバースプロキシで `/api/` を転送）。CORS は許可しない | 02 §2 |
| 12 | 最終ログイン日時 | 残す。**ログイン完了時に更新**（BFF のため `auth_time` 判定は不要） | 01 PF-USR-05 |
| 13 | 認証方式 | **BFF**。ブラウザにトークンを置かず、サーバー側セッション（Redis）+ HttpOnly Cookie | 01 §7.2、02 §5.2 |
| 14 | セッションの単位 | プレーン毎に分離。**AP はブラウザあたり 1 テナント** | 01 §7.2 |
| 15 | CSRF 対策 | `SameSite=Lax` + 変更系のカスタムヘッダー必須 + `Origin` 検証 | 01 §7.3、03 §1 |
| 16 | データベース | **CP と AP で DB を分ける**（`control_plane_db` / `app_db`） | 01 §9.1 |
| 17 | DB ロール | プレーン・用途毎に 6 ロールへ分離。**RLS をバイパスするロールは作らない** | 01 §9.2、02 §4.1 |
| 18 | プレーン間依存 | AP→CP はレジストリ公開ビューの参照のみ、CP→AP は集計・物理削除のみ（テナントコンテキスト設定下） | 01 §4.3 |
| 19 | IdP の管理権限 | 払い出し用 SA（master）とテナント毎のユーザー管理用 SA を分ける。AP は払い出し用 SA を使わない | 01 §7.1、02 §3.1 |
| 20 | クライアントシークレット | 保存せず、シード値から HMAC で導出 | 02 §3.3 |
| 21 | 予約語の管理 | バックエンドを正とする。フロントは静的ルートの優先と存在確認 API で判定 | 02 §5.4 |
| 22 | テーブル命名 | 既存規約を維持（`t_` 接頭辞・単数形）。ビューは `v_` | 02 §4.3 |
| 23 | ID | UUIDv7、PostgreSQL `uuid` 型 | 03 §4 |
| 24 | エラー形式 | RFC 9457 Problem Details。他テナント・閲覧範囲外は 404 | 03 §2 |
| 25 | ページネーション | カーソル方式（`limit` / `cursor` / `next_cursor`） | 03 §3 |
| 26 | 楽観ロック | `version` 列 + `ETag` / `If-Match` | 03 §5.2 |
| 27 | 論理削除 | `deleted_at`。一意制約は部分インデックス | 03 §5.1 |
| 28 | ログ | 1 行 1 JSON を標準出力。必須フィールドと秘匿値の禁止を規定 | 03 §6 |
| 29 | 監視 | 観点のみ定め、実装は本フェーズの対象外 | 04 |
| 30 | 文書構成 | 共通基盤（技術非依存 / 技術依存）とテーマ固有に分離 | README |
| 31 | 払い出し時の AP の初期データ | CP から AP に書き込まず、**AP がログイン完了時に作る**。初期管理者のユーザー行はログイン時の同期で作り、デフォルト組織は組織の行が 1 件も無い（論理削除済みを含む）ときに作る。CP → AP の依存を集計・物理削除に保つ（`app_cp_agent` に INSERT を与えない） | 01 §6.2、§8 PF-USR-04 / PF-ORG-04、02 §4.7 |
| 32 | 無効化したユーザーのセッション失効 | AP の各リクエストで `t_user.is_active` を確認し、無効（または行が無い）なら BFF のセッションを破棄して 401。あわせて IdP のユーザーを無効化し IdP のセッションも失効させる（リフレッシュトークンを無効にする）。キャッシュや失効リストは持たない | 01 PF-USR-03、02 §5.1 |
| 33 | ユーザーの姓・名・ロールの保持 | **Keycloak を正としたまま、一覧表示用の写しを `t_user` に持つ**（`first_name` / `last_name` / `roles text[]`。`roles` は `tenant_admin` / `member` のみの CHECK）。ログイン時の同期と管理者の変更時に更新する。一覧でロールを出すための 1 件ずつの IdP 問い合わせを避ける。ロールの判定（認可）は引き続きトークンのロールを正とし、写しは使わない | 01 §9.4、02 §4.7 |

## 2. 将来の方針検討事項

現フェーズの未決事項とは分けて管理し、規模や運用要件の見通しが立った段階で決定する。

| # | 論点 | 内容 |
| --- | --- | --- |
| 1 | 大量テナント時の対応方針 | 「1 テナント = 1 レルム」はレルム数の増加に伴い Keycloak の起動時間・メモリ・管理コストが増える。大量テナント時は「単一レルム + Organizations 機能」方式などを比較検討する |
| 2 | 同期払い出しの見直し | テナント数・処理時間の増加に応じて、バックグラウンドジョブ / ジョブキューへの移行を検討する。**#1 と同じタイミングで検討する** |
| 3 | ログ収集・可視化基盤 | ログを収集・蓄積し、アクティブユーザー数（日次/月次）などを可視化する構成を検討する。CP ダッシュボードとの連携方法もあわせて決める |
| 4 | 監視基盤 | 04 の観点を実装する基盤（メトリクス収集、トレース、アラート通知）を選定する |
| 5 | 複数テナントの同時ログイン | 同一ブラウザで複数テナントにログインする要件が出た場合のセッション設計 |
| 6 | プレーン間依存の解消 | レジストリ参照の API 化、メトリクスのイベント化、CP / AP のサービス分割 |
